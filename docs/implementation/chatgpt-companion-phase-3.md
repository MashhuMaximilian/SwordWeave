# SwordWeave companion Phase 3 build plan

Updated 2026-11-23. A player asks a rules question, checks their character's current state, or approves a note, consequence or supported build change during play. The first release operates on one selected character per action. It uses the [shared delivery contract](chatgpt-companion-roadmap.md#shared-implementation-and-release-rules), the [Phase 1 build plan](chatgpt-companion-phase-1.md), and the [Phase 2 editing plan](chatgpt-companion-phase-2.md).

## Dependencies and permissions

Reuse Phase 1's rules answers and verified identity, and Phase 2's character selection and permanent build review. Set `MCP_CHARACTER_PLAY_READ_ENABLED` and `MCP_CHARACTER_PLAY_WRITE_ENABLED` off by default. Use `swordweave:read` for authorized reads and `swordweave:play` for preparing and applying notes and runtime actions. The Phase 3 flags own those new operations and live context reads. A permanent build change remains a Phase 2 operation in either character mode, with its own permissions, scope and flags. Phase 2 tools accept no runtime mutation fields.

Apply the [platform Markdown rule](user-authored-markdown.md) to player notes and consequence descriptions in review and saved display. Keep compact names and mechanical fields in their current formats. If a player asks about an attached monster, direct them to its authorized [play sheet](character-monster-companions.md#player-flow) for its independent Vitality or consequences, its Bestiary reference for rules, or the character's [Print and Download PDF controls](character-monster-companions.md#dedicated-character-pdf-pages) for its dedicated printed page. Phase 3 runtime tool actions operate on the selected player character.

| Operation | Companion permission and data boundary |
| --- | --- |
| Ask a rule question | Reuse Phase 1 rules access. Retrieve a sheet only after the player selects a character and the actor passes its read policy. |
| Read canonical current/max Vitality and supported runtime state | `EDITOR` or `OWNER`, matching the current character play-state GET. Condition details and package history follow the more restrictive operation below. |
| Read character game history or full consequence occurrences | `OWNER`, matching the dedicated routes. Project event summaries and relevant fields only. |
| Append to player notes | `EDITOR` or `OWNER`, matching the existing notes edit. Show and approve the exact proposed addition. GM-only notes stay outside this slice. |
| Manually set current Vitality | `EDITOR` or `OWNER`, using the character play-state path. Verify the current and maximum values and applicable runtime revision. |
| Record or resolve a consequence, or apply a sourced consequence package | `OWNER`, using the appropriate consequence operation. Use the exact reviewed occurrence or package and its current state. |
| Apply a permanent in-play build change | Phase 2 owner/editor apply or suggester proposal permissions. The workspace rules govern the request. A character's permanent progression and live state remain separate. |

Resolve the active actor again inside each commit. Never use the editable play-state override map as a general tool input. The website has multiple routes that accept different consequence mutations and roles. Keep each companion action on its designated route's authority. Do not give an editor owner-only read or consequence operations by forwarding raw overrides. ## Milestone 3.1. Read rules and current play context

- `read_character_play_state({ characterId })` returns character ID, projected revision, current and maximum Vitality, and supported runtime markers with viewer-safe names. Include up to 20 active consequence summaries only for the owner, with occurrence ID, revision, duration and a visible rule source when available. Return up to 20 eligible source choices for the owner as `{ sourceKey, name, versionId }` in name and key order. Source keys use the native `primitive:<positive decimal ID>`, `effect:<UUID>` or `capability:<UUID>` shape. List only usable, authorized sources in this character's graph with a supported consequence package. Omit restricted package choices and link the same-origin sheet for results outside the cap. Project permitted fields only.
- `read_character_history({ characterId, cursor? })` returns at most 20 owner-visible entries and a cursor bound to the actor and character. Sort by `createdAt` descending then log ID descending. Whitelist summaries for Vitality changes, rest, and capability triggers. Use typed fields and a safe display name from authorized sources. Skip types that lack a safe projection. Do not disclose raw event payloads, another sheet's history or a hidden target's identity.
- Use a top-level `REPEATABLE READ, READ ONLY` transaction for the companion's play read and preview, with no row locks or initialization. Read the permitted existing state, authoritative nullable character Vitality and canonical occurrences in the same snapshot. Use `emptyPlayState()` for a missing row. Extract pure `projectCanonicalPlayState(stored, canonical)` from `reconcilePlayState` and share its field-clock and reference logic with the website reconciler. Return the projected revision as a view of the canonical values. Review payloads capture the projected action-specific baseline and its field clocks. At commit, recompute that same projection under the native locks, reject changed reviewed dependencies, then reconcile to storage and use the actual post-reconciliation revision as the native command's base. Test absent and divergent stored rows and a real intervening edit.
- Use the designated website path's `loadCharacterMaxVitality` for current play parity. For a historical pinned modifier, verify equality with the version-pinned sheet calculation before a Vitality-changing action proceeds. If they differ or a dependency is unavailable, omit the unresolved derived value and block the action with a sheet link. Keep the existing website calculation during this slice. Authorize source roots and all displayed dependent pieces before presenting names, package choices, restrictions or history derived from them.
- When a rules answer uses current context, state the relevant sheet facts and link the rule and version. Keep suggestions and table rulings distinct from recorded facts. Ask for clarification when the intended target, duration or rule remains ambiguous.

Exit when a rules-only exchange works without a character read, a linked editor can read allowed runtime state, the owner can read bounded history, and a suggester, viewer or revoked actor receives only their allowed surface. Assert no state initialization, reconciliation writes or log entries from companion reads. ## Milestone 3.2. Review and append a player note

- `preview_session_note({ characterId, text })` accepts 1–2,000 characters of Markdown after trim and CRLF normalization. Return the target name, exact text, and the resulting append preview. Show only the proposed addition and permitted adjacent context. Retain player formatting and never generate tool instructions from previously saved notes.
- `prepare_session_note({ characterId, text, supersedesOperationId? })` returns the shared approval response and stores a `session_note` operation bound to the exact character, actor, normalized text and current player-notes digest. `save_session_note({ operationId })` calls the Phase 1 append helper under current permission. Return the original append result and applied revision with the sheet link. Any newer authorized revision is labeled current. The action changes only the note and the required revision and receipt.
- Commit the append and the companion receipt together. If the website changed the notes after review, return a new preview and require another approval. Match the browser note-specific lock behavior. The website's ordinary edit path continues owning its replacement semantics. [Website notes write and revision](../../src/app/api/characters/%5Bid%5D/route.ts) · [Character mutation transaction](../../src/lib/character/mutation-transaction.ts)

Exit when an editor and an owner can each append a reviewed note, an unauthorized actor cannot, the same operation appends once across a lost-response retry, and concurrent site edits survive. Check notes content, game state and the receipt from separate database sessions.

## Milestone 3.3. Review and apply a play action

`preview_play_action({ characterId, action })` returns `{ characterId, actionKind, before, after, source, tableQuestions, blockers }`. `prepare_play_action({ characterId, action, supersedesOperationId? })` rechecks the same narrow contract and persists an immutable `session_play_action` review. `apply_play_action({ operationId })` resolves the approved action and returns `{ operationId, status, appliedRevision?, appliedOccurrences?, result, sheetUrl }`. Use exactly one strict action shape from the tagged union. Require the native UUID, decimal ID or string occurrence ID for each authorized selector.

| Action input | Preview and apply contract |
| --- | --- |
| `set_current_vitality { value }` | Accept a nonnegative safe integer and normalize to the clamped value before change detection. Bind the raw nullable value, displayed value, max and projected field revision. If the clamped value equals the displayed value, return a no-op receipt and preserve the stored value, including dynamic-full null. Otherwise map to one absolute `currentVitality` mutation with the approved UUID and `source: manual`. Recompute under lock and preserve the normal revision and log for an actual change. |
| `record_consequence { title, description?, durationTier }` | Use title up to 200 characters, description up to 2,000, and `manual`, `short_rest` or `long_rest`. Custom occurrences carry no authored Vitality delta or modifiers. Bind a server-generated occurrence ID, expected missing revision 0, `source: custom` and active status. The inserted occurrence has revision 1 and the server commit time. Treat the tier as descriptive and use the dedicated resolution command to end it. |
| `resolve_consequence { occurrenceId, expectedRevision }` | Resolve the exact active occurrence under the dedicated owner operation. Preserve application provenance and history. Show restrictions that end and any derived changes. Re-read the full occurrence and revision under lock. Use the existing provenance-preserving save. Ending an occurrence does not refund the original Vitality delta. Replay the original receipt on repeat. |
| `apply_consequence_package { sourceKey }` | Take an authorized source key from the play read. Extract the native package preview and apply body to an actor-aware service. Check owner authority independently at each caller. The website keeps its existing literal Clerk owner check. The companion additionally requires the verified native owner and supports that same owner binding for the initial package write. Return unavailable for an unsupported legacy internal-ID owner on this adapter and include both formats in tests. Check the current usable path and all source pins before projecting any data. Bind the source, complete dependency digest, availability, package hash, current nullable Vitality, max and predicted occurrences. Recompute under lock, then call with the approved UUID, expected package hash and nullable Vitality. Preserve canonical occurrence snapshots, history and native receipts. |

The read-only preview reports effects supported by existing rules and leaves all writes to the canonical commit path. The tool displays the current state, proposed new state, affected subject, allowed source, duration and any calculation warning. A confirmed narrative note goes through Milestone 3.2. Mechanical effects use the typed tools above. Website-only flows include restore/import, undo, rest automation, capability roll automation, arbitrary custom modifiers and applying one action to several subjects. The player can still ask about those rules.

Keep the transaction ordering from Phase 2: lock the companion operation, then character, then publishing if the exact operation uses it, then native play-state rows. Reconcile legacy and canonical values inside the mutation transaction. Recheck actor access, current revision or occurrence, and all relevant displayed dependencies after locking. Preserve existing unrelated-field merge semantics only when the unaffected changes do not alter the reviewed outcome. If a dependency changed, apply nothing, show the refreshed preview, and require a new approval. Never silently substitute another source or issue a second command on an uncertain result.

Use the operation UUID as the native command ID. Manual occurrence writes update the canonical consequence and native command receipt. Package writes also apply the native pre-application-max Vitality calculation and emit the native log. Preserve each operation's storage and side effects. Subsequent reads project canonical changes without persistence. The website reconciliation or the next runtime mutation stamps the play-state row through the shared helper. Keep the original result in the companion receipt and label any newer authorized state separately. Verify replay, stale baselines, duplicate in-flight requests and expiry. Invalidate resolver caches after commit. [Consequence validation](../../src/lib/character/consequences/validation.ts) · [Package preview and apply](../../src/app/api/characters/%5Bid%5D/consequences/apply/route.ts) · [Native receipt state](../../src/lib/play-state/service.ts)

## Milestone 3.4. Permanent changes during play

Reuse the Phase 2 edit preparation and commit tools for an authorized, reviewed permanent change during the session. Show the build change, cost, remaining Build Units and current play implications separately. Run the existing authorized draft path in the applicable character mode and verify it matches the supported website behavior with the same character state. Preserve untouched conditions, current Vitality, history, and personal notes. If the current mode or rules disallow the change, offer an explanation or the existing sheet control. The companion does not change the mode just to force a write through.

The first in-play slice uses the resources already available to the character. Owners use the [Phase 2 level advancement review](chatgpt-companion-phase-2.md#reviewed-level-advancement) to change level. Its own approval, accounting and release gates apply during play as well.

Release after verifying these journeys in the intended ChatGPT surface and their matching website paths:

1. Answer a rules question without a write. Read a character with and without a persisted play-state row and check that neither read creates writes. Keep owner history and consequences out of editor/read-only responses.
2. Append an approved note and replay the same request. Verify one append and identical game state. Change notes on the site between preview and commit and require a new review.

Exercise the shared, operation-bound host approval with text-only and optional card responses. Test the website staging confirmation separately.

Enable context reads before writes. Run a representative practice session with synthetic data and record the full accepted path and the denied cases. Rollback disables Phase 3 tools and leaves saved notes, history and any applied changes available on the site.
