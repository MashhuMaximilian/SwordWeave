# SwordWeave ChatGPT companion Phase 1 build plan

Updated 2026-11-25. The [delivery plan](chatgpt-companion-roadmap.md) maps the full companion and owns the [shared approval and status contract](chatgpt-companion-roadmap.md#tool-and-approval-contract-across-phases). This document details the Phase 1 milestones. The approved scope and release order are in the companion design.

## Evidence and design constraints

One Free web account installed and invoked a private custom MCP plugin over HTTPS. After an ordinary character discussion, the tool received the previously discussed fictional name and compass detail and rendered a card. A separate chat worked with a player-provided recap. The browser downloaded the sample PDF from the link in chat and its SHA-256 matched the fixture. A second private installation completed synthetic OAuth and worked in a pre-existing conversation. A protected write, repeat and read-back returned the same receipt. The fixture used an in-memory identity and data store. Milestone 1 verifies real Clerk identity against isolated SwordWeave data. The fixture write had no separate confirmation, so the experiment does not verify production save approval. [Free-account experiment](chatgpt-companion-free-account-check.md)

Ship Phase 1 in the existing SwordWeave project as a stateless Node.js Next.js route at `/api/mcp` using Streamable HTTP. Start from the demo’s MCP SDK and Apps bridge pattern. Use the installed-prototype pins of `@modelcontextprotocol/sdk@1.32.2` and `@modelcontextprotocol/ext-apps@2.0.4` until compatibility tests justify a change. Validate the web-standard server transport on Next.js. Configure a stable HTTPS URL for staging before OAuth verification. The public plugin goes through the OpenAI submission path after staging acceptance. Review eligibility on Free after publication. [MCP quickstart](https://developers.openai.com/plugins/build/app-quickstart) · [Connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt) · [Submission](https://developers.openai.com/plugins/deploy/submission)

### Creation draft and version selectors

Use a strict `DraftV1` shared by preview and prepare. Its fields are `schemaVersion: 1`, `name?`, `attributes?: { physical?, mental?, magical?, proficient? }`, `size?`, `pieces?`, `placements?`, `backstory?` and `portraitPrompt?`. Use the site's character size, attribute and proficiency validators. The first starter journey uses the normal level-one pool, with starting access and budget verified before save. Accept the existing six player backstory fields and up to 2,000 characters of portrait guidance for discussion. Keep the portrait prompt out of save and receipt storage. Future progression uses its own tool. Preview can show missing fields, while prepare rejects missing required mechanics and validates every selected piece. Any defaults used in a save appear in the review.

- `PinnedRef` is the catalogue's `{ kind, id, versionId }`. Primitive IDs are positive decimal strings and other entity IDs and version IDs are UUIDs. A dependency is either `{ pin: PinnedRef }` or `{ pieceKey }` referring to the same draft. Keys are unique 1–32 ASCII letters, digits or underscores. A `piece` is `{ key, action: "reuse", pin }`, `{ key, action: "create", kind, fields, members? }` or `{ key, action: "fork", from: PinnedRef, changes?, members? }`. Changes are a sparse patch to reviewed canonical fields. A provided member array replaces the source member list. Unknown fields, invalid role and kind combinations, dangling aliases and cycles fail before approval.
- An ordered member is `{ ref, isMirrored?, quantity?, role? }`. Use the existing positive integer quantity and capability role parser. Accept role only on a capability's primitive slot. Use an explicit adapter whitelist by kind below. A root placement is `{ pieceKey, source, isMirrored? }`. Sources are `LINEAGE`, `UPBRINGING`, `MANIFEST` or `PERSONAL` for primitive and capability placements, the matching heritage kind for a heritage, and `ITEM` for an item. Root mirroring applies only to eligible primitives. Each placement is an occurrence. Effects are available as authored or reused dependencies of a capability or item. The initial character POST does not attach standalone effects.
- After strict parsing, canonicalize with `canonicalJsonStringify` while preserving ordered member and placement arrays. Topologically order dependency steps using input order to break ties. Generate and persist stable step UUIDs server-side. Resolve aliases to previously committed step entity and version IDs and retain the normalized graph digest and exact referenced source pins. The character step comes last. Reject attempts whose legacy snapshot or association data cannot reproduce the approved nested graph.

| Kind | Companion authoring input and slot persistence |
| --- | --- |
| Primitive | Explicit name, narrative rule, category, cost tier and BU, with existing typed market, mechanical and mirror fields where valid. Use the primitive POST rule validators. Resolve direct placements as `primitiveInstances` or source-scoped primitive occurrences and persist approved primitive versions on `characterPrimitives`. |
| Effect | Name and narrative description, with ordered primitive members. Map quantity and mirror to `primitiveSlots`. Reuse the effect primitive parser and junction. Resolve the resulting effect version through parent dependency pins. |
| Capability | Name, verbose description, native capability type and source type. Split primitive/effect members into `primitiveSlots` and `effectSlots` using the existing parsers. Persist approved capability roots on `characterCapabilities` and expand its approved versioned members. |
| Heritage | Name, description and native heritage kind, with lineage size when applicable. Map primitive members and capabilities to the existing slots. Persist the approved template version on `characterHeritages` and expand its approved member pins. |
| Item | Name, description, native item type, size, rarity, BU and slot cost, with the existing item quantities and equipment flags where supported. Map the primitive, capability and effect members to the item parser. Persist the approved item version on `characterItems`. |

Use the existing version reconstruction and dependency-pin helpers to rebuild input graph edges. Feed those ordered edges to the shared bundle preparation. On the companion branch pass explicit reviewed root and expanded slot pins into persistence instead of resolving latest inside the insert loop. Persist independently authored dependency associations with their reviewed pins. Test one nested capability or heritage in preview, saved junctions, canonical sheet and cost calculation. If a writer cannot preserve the pins, close that adapter until its specific mapping and tests pass.

The local fork adapter accepts a current authorized FULL primitive source that the supported private primitive validator can reproduce. It previews the source name and exact version, stores the source pin and snapshot digest with the private fork, and checks source access at approval and at every save step. A new fork needs a supported field change. Name conflicts are scoped to the actor and source, and a retry returns the original receipt.

The private capability adapter accepts current authorized primitive pins and primitive aliases in the same draft. It requires explicit member roles, preserves quantities and order, and calculates the native component cost. The coordinator commits newly authored primitive dependencies first and substitutes their verified persisted pins in the capability snapshot. It saves the root, memberships, version and receipt together before attaching the capability in the character step. Effects and mirrored members require their own supported adapters.

Private capability forks use a current FULL source with reproducible primitive members and native fields the starter can copy. Omitting `members` retains their order, roles, quantities, labels, notes and version pins. Supplying `members` replaces the complete list. The review binds the source version, its snapshot digest and the original child version digests even when the replacement removes those children. The native fork records that provenance privately. A second player can choose the same fork name independently.

## Milestone 3. Review, save and recover

### Server contracts

* `prepare_character_save({ draft, supersedesOperationId? })` validates `DraftV1` and returns the shared approval response for a `character_create` operation. Store private, normalized inputs and version-pinned dependency steps. Limit each operation to 20 steps including the character, to 64 KiB of canonical JSON and to ten seconds per execute invocation. Prepare and approve commit no domain steps. The next user-requested continuation advances the first step.
* `get_operation_status({ operationId })` returns the requester's currently readable receipts and the next action. `continue_character_save({ operationId, stepId? })` advances only a `character_create` under valid approval and unchanged reviewed dependencies. Multi-step saves require the step ID returned by status. Retry an uncertain step with the same ID to recover its receipt without advancing another step. If a later step is permanently blocked, retain the earlier private results and state which step stopped and why. The player can review a fresh save using eligible earlier results as pinned reuse.
* Use the shared staging review protocol. Test one approved save with the exact payload digest, wrong actor and stale review denial, double confirmation and reconnect. Production write admission follows the shared host approval gate. [Shared approval and status rules](chatgpt-companion-roadmap.md#tool-and-approval-contract-across-phases)

### Durable state

Use `companion_operations` and `companion_operation_steps` for shared coordination. Store operation UUID, owner user UUID, kind, schema version, subject kind and ID, canonical proposal JSONB, SHA-256 proposal and nonce digests, nonce expiry, approval timestamp, trusted approval source, state, last activity, expiry and a versioned terminal receipt JSONB. Store a nullable superseding operation UUID for status. Keep kind, subject and actor after payload cleanup so read-back dispatch can still authorize. Operation states are `pending_approval`, `approved`, `completed`, `blocked` and `superseded`. Retryable interruptions leave the operation approved and roll back the failed write. A stale review or deterministic terminal block stores its stable reason with no domain mutation in that attempt. If detected after domain SQL, roll back first, then record the block under a new operation lock only if its reviewed step and state still match. Steps hold the operation UUID, stable step UUID, ordinal, state, committed entity kind and text ID, version pin and failure code. Step states are `pending`, `committed` and `blocked`. Use primary key `(operation_id, step_id)`, unique `(operation_id, ordinal)`, FK cascade from operation to steps, and indexes on `(owner_id, id)` and `expires_at`. The step table is for coordinated creations. Single-action receipt variants carry the edit revision and changed slot IDs, proposal subtype, native ID and decision, note revision and appended digest, or original Vitality and occurrence results, as applicable. They omit free-text input and are projected under current access. Results link to domain rows without a deletion cascade to those rows.

Use the shared `READ COMMITTED` lock and authorization order. Confirm operation state and expiry, then read entity versions and permissions after the publishing lock is acquired. A later progression note is a separate operation with its own character lock. Run each domain step and its receipt in the same transaction. After a transient or uncertain failure, read the receipt outside that transaction before making a new attempt. Each successful invocation advances one step. Propagate non-success out of the owning `withDatabaseTransaction` so earlier SQL rolls back, including errors converted to HTTP responses by existing wrappers. Verify authored rows, associations and version snapshots share that transaction. Keep network calls and asset uploads outside the atomic step. Block a step until its effects and receipt reconcile safely.

Use the shared lifetimes. Run `pnpm exec tsx scripts/expire-companion-operations.mts` hourly on the selected application's scheduler. Take a job-specific transaction advisory lock and select up to 200 expired operations by expiry and UUID with `FOR UPDATE SKIP LOCKED`. Recheck expiry while locked and remove only expired companion rows and cascading step or progression document rows. Commit each batch, with a maximum of five batches per run. Test a competing save with a held row lock, deletion at progression expiry, preservation of native domain rows and running the older application revision alongside the additive schema.
