# SwordWeave companion Phase 2 build plan

Updated 2026-11-25. A player chooses an existing character, sees the effects of an edit, and applies or proposes the reviewed changes through SwordWeave's existing roles and history. Character owners can also review advancement to a specific level. Use the [delivery plan](chatgpt-companion-roadmap.md) for shared approvals and rollout and the [Phase 1 plan](chatgpt-companion-phase-1.md) for the MCP transport, catalogue filtering and recovery foundation.

## Dependencies and permissions

Start after Phase 1 proves strict Clerk identity mapping, safe responses, and a player action that approves an immutable payload. Keep independent `MCP_CHARACTER_EDIT_READ_ENABLED` and `MCP_CHARACTER_EDIT_WRITE_ENABLED` flags, off by default. Phase 2 reuses `swordweave:read` for reads. Provision `swordweave:edit` for preparation and writes, and verify ChatGPT's scope upgrade in staging. Scopes limit the app. The existing character role limits each operation.

Apply the [platform Markdown rule](user-authored-markdown.md) to backstory edits, proposal rationale, decision notes and other prose. Test that previews and saved reviews show the same visible formatting. For [monster companions](character-monster-companions.md), use the same-origin sheet handoff to direct players to Edit mode, where they can attach individually tracked monster play copies and access their Bestiary references. Any later attachment projection requires current character and monster access.

| Operation | Existing permission that must hold |
| --- | --- |
| List characters or read a safe sheet projection | Active account with ownership or share. The roster includes owned and active shared rows only. Public Library access goes through the Library tool. |
| Preview an apply or prepare its review | `EDITOR` or `OWNER`. |
| Preview a proposal, prepare it or submit it | `SUGGESTER`, `EDITOR` or `OWNER`. A submitted proposal changes no sheet fields. |
| Inspect an existing build proposal | Its author or the character owner, under current access. |
| Approve or reject a proposal | Character `OWNER`. Approval also rechecks the author's current suggestion permission and their source access. |
| Withdraw a workspace proposal | Its author under current access. A resolved proposal cannot be applied again. |
| Preview, prepare and apply level advancement | Character `OWNER`. Preparation and application also require `swordweave:edit`. |
| Create and attach a new private piece | Character `OWNER` with both `swordweave:create` and `swordweave:edit`. |

Use the verified actor's Clerk ID and internal UUID. Check owner rows in both existing ownership formats and use the same active-share role rules as the website. The authenticated companion must resolve the exact linked user. Do not invoke the local website username fallback or infer an account from any model-supplied ID. Return the same unavailable outcome for an unknown character and an unauthorized character. Permission checks precede reads of `readWorkspace`, proposal records and nested sources. ## Milestone 2.1. Authorized roster and build context

- `list_accessible_characters({ cursor? })` returns `{ items, nextCursor }`. Each item contains only `characterId, name, level, permission, sheetUrl`. Query rows owned by the linked Clerk ID or internal UUID and rows with an active share for the internal UUID. Then resolve the effective role using the existing permission policy. Order by lowercased name and UUID and return at most eight entries. Use the Phase 1 signed cursor with a character-roster purpose, actor and expiry. Construct same-origin sheet links on the server.
- `read_character_build({ characterId })` returns `{ characterId, name, permission, revision, foundation, slots, budget, partial, sheetUrl }`. Include size, level, attributes, known Build Units and up to 40 actionable slots. Each visible occurrence returns its ordered path of edge IDs from the character root, its permitted occurrence ID, kind, name, pin, location, mirror state and whether its path can select a destination container. Only return paths through authorized nodes. Report a partial view for restricted or truncated results and link the sheet. Exclude DM notes, personal notes, draft contents, owner IDs and raw graph metadata. Return authorized budget totals when the slot limit truncates the list. Omit them when sheet dependencies are restricted or unresolved. The budget reports ordinary BU remaining, applied and available drawback credit, uncovered excess, and separate Item BU. Preview re-resolves each path from the character's current graph.
- Read using `readWorkspace` and the existing sheet calculator, with a server-side projection that checks access before reading data into the tool response. Do not forward the workspace GET or the complete character roster JSON. Status and permissions are fetched again on each tool call.

Exit when staging shows owner, editor, suggester and viewer selection working from chat. A revoked share disappears on the next read. A public-only viewer has no companion workspace access. Streaming and truncation must keep the result usable in text. [Workspace read](../../src/lib/character/workspace/read.ts) · [Sheet calculation](../../src/lib/character/workspace/draft-sheet.ts)

## Milestone 2.2. Preview the exact changes

`preview_character_edit({ characterId, expectedRevision, intent, changes })` returns `{ characterId, revision, changes, budgetDelta, blockers, tableQuestions }`. `intent` is `apply` or `propose`. Require one to 12 ordered changes, strict schemas and at most 64 KiB of canonical request JSON. Use exact selectors from the graph. Derive author ID, command ID, branch, source hashes and version bindings on the server. The first slice admits these inputs:

| Change input | Mapping and expected behavior |
| --- | --- |
| `set_foundation { fields }` | Map to a `character` draft operation. Whitelist `name, attrPhysical, attrMental, attrMagical, attrProficient, size, backstory`. Merge only supplied backstory keys from `description, personality, origin, motivation, ties, flaw` into existing backstory. Run the site's field validators on the merged foundation, including the full attribute sum. Exclude progression, notes and play overrides. |
| `attach_library_piece { ref, channel, isMirrored? }` | Take the Phase 1 catalogue pin. Map to a `create` draft operation with `existingId`, empty `draft`, native `kind`, `category: channel` and `mirrored` where supported. The initial adapter accepts only a requested pin that equals the reproducible effective version and whose complete authorized nested pin set matches the reviewed graph. Verify in the locked create branch before insertion and verify the written version and graph before receipt. Reject unavailable, historical or conflicting pins in this slice. |
| `remove_reference { path }` | A one-edge path maps to `detach` with the child as target. A nested path maps to `remove-reference` with the final edge as `edgeId`, its parent as target and the preceding edges as the target path. |
| `move_reference { path, destinationPath }` | The initial slice moves a nested membership to another eligible container. Map to `move-reference` using the same source split as removal and resolve the destination path to its container target and content hash. Reject a root move, an invalid or ambiguous destination or the same source container. |
| `mirror_primitive { path, isMirrored }` | Use `mirror-instance` for a direct primitive and `mirror-reference` for an eligible nested primitive, with the same container and edge split. These native commands toggle. Check current mirror state and skip if the approved value already matches. Validate drawbacks and credit. |

`ref` uses a decimal string ID for primitives and a UUID for other kinds. Paths contain 1–20 ordered edge IDs from an authorized root to the occurrence. Each consecutive edge must join the previous child. Reject disagreement or missing edges. Derive native target, content hash, expected revision, destination hash and command IDs in order from the executing graph. Build channels follow `LINEAGE`, `UPBRINGING`, `MANIFEST` and `ITEM`. Reject incompatible kinds, mirror values or destinations. Verify reproducible current pins and their dependencies for eligible effects, heritages, items, primitives and capabilities. Supported remove, move and mirror paths use the native workspace commands. Native private capability forks required by a supported nested change retain verified author ownership.

Translate to server-generated `DraftOperation` values. Extract a rollback-only preview wrapper from the existing draft service. Acquire the character and relevant publishing locks, check the actor and revision, capture the build fingerprint and graph, then run the evaluator. Catch the rollback sentinel only outside the transaction that owns preview. Keep hooks free of external side effects. Today `workspace/save-entity.ts` calls website handlers using synthetic requests. Route workspace creation and container saves through Phase 1's narrow actor-aware services with an explicit verified actor. Direct edits run as the requester. Proposal preview and execution use the active author for source access and authoring, with the character owner's permission checked separately on owner decision. Compare the pre-commit result with the approved semantic diff in the same transaction. Normalize preview-generated row IDs and timestamps to operation-local identities. Compare paths, pins, cost and changed content. Roll back on mismatch. Check all sources before presenting the diff and again at commit. Show normal budget warnings and validation failures distinctly.

Keep the website drafts' own IDs and versions. A companion preview or prepared review never overwrites an editing draft. Applying a separate approved companion edit advances the sheet revision and an older website draft follows its existing stale path. Play-only changes stay out of the build fingerprint where the existing workspace does so. If a reviewed result depends on a play field, bind that field too.

`prepare_character_piece` previews one new private primitive, effect, capability, heritage, or item on a saved character. An effect can contain primitives. A capability can contain primitives with native roles and effects. A heritage can contain primitives and capabilities, and its kind must match the character tab. An item can contain primitives, capabilities and effects, and uses the Item BU ledger. Every nested member must have an exact, reproducible current version authorized to the owner. Legacy effect-condition graphs, historical or conflicting versions, and nested mirrors remain in the website composer.

Use the native authoring and attachment services in a rollback-only preview. Show the fields, ordered members, descendant pins and budget before and after. `apply_character_piece` saves the private definition, its version and junctions, exact placement, workspace revision, character snapshot and receipt together under owner, character and publishing locks. Retry using the same operation ID. To build a chain of new components, approve the leaf first, then use its returned pin in the parent review. The initial starter draft still accepts primitives and primitive-member capabilities. Create the other pieces from ChatGPT after the starter save.

Exit with before/after text and optional card matching the canonical preview for names and attributes, one pinned library attach, one removal or move, and one supported mirror. Verify preview leaves character, entity and receipt rows unchanged. Reject stale revision, mismatched occurrence, expired authorization and denied nested content. ## Milestone 2.3. Prepare, apply and review proposals

| Tool input | Output and server behavior |
| --- | --- |
| `prepare_character_edit({ characterId, expectedRevision, intent, changes, rationale?, supersedesOperationId? })` | Re-run preview and persist a review through the shared contract. Return `operationId, summary, approvalUrl, expiresAt`. Store the actor, selected character, intent, normalized operations, base revision, base fingerprint, expected pins and semantic diff. Allow rationale only for `propose`, up to 2,000 characters. Create no draft, proposal or sheet mutations during preparation. |
| `apply_character_edit({ operationId })` | Execute the approved `character_edit` operation under `EDITOR` or stronger access. Use the workspace draft executor to apply the reviewed operations in one character transaction, preserving its snapshot and revision handling. Return `operationId, status, resultRevision, changedSlots, sheetUrl` after committed read-back. |
| `submit_character_proposal({ operationId })` | Use the approved `character_proposal_submit` operation and call `submitCharacterProposal` with normalized operations, captured revision, expected base hash, rationale and operation UUID as `requestId`. Return `proposalRef, status, sheetUrl`. The owner decides through a separate operation. |
| `list_character_proposals({ characterId, cursor? })` and `read_character_proposal({ characterId, proposalRef })` | Show up to eight visible proposals ordered by updated time then native ID descending, with a scoped cursor. Check owner or author access and the exact character before emitting the safe summary. Read returns `proposalRef, status, baseRevision, description, diff?, sheetUrl`. For a pending proposal, use rollback preview where authorized and report stale state if needed. |
| `prepare_proposal_decision({ characterId, proposalRef, decision, note?, supersedesOperationId? })` then `review_character_proposal({ operationId })` | For workspace proposals, decisions are `approve`, `reject` and `withdraw`. Use a separate `character_proposal_decide` review and exact native role. Bind native proposal ID, pending status, content digest and reviewer note up to 2,000 characters. Approval also binds the reviewed base fingerprint and pins. Reject and withdraw can decide an unchanged stale pending proposal without applying a draft. Only approval enters the author-scoped executor. Return terminal status and the applied revision where present. |

Native workspace proposal IDs embed the author identity. Use an opaque `proposalRef` containing the actor, character, subtype, native ID and ten-minute expiry, sealed with AES-256-GCM and a random 96-bit nonce. Derive its key from the server secret with HKDF-SHA-256 and a distinct versioned proposal-ref context. Bind the read cursor to the same actor and character and seal its native ID key. Issue fresh references from list, submit and authorized status. Resolve and authorize them again on read or prepare. Commit resolves the stored native ID and rechecks access. Use the character's sheet link.

Version-only proposals are a gated follow-on. `prepare_version_proposal({ characterId, path, proposedVersionId, rationale?, supersedesOperationId? })` takes the existing slot path and a version of the same definition, from the eligible catalogue pin or the website. Derive the current version, `targetKind`, target ID and primitive instance ID from that exact slot. Admit native `PRIMITIVE`, `CAPABILITY` and `ITEM` only. Use the native suggester-or-higher submission rule and owner-only approve or reject. Limit rationale and decision note to 1,000 characters. Dispatch shared proposal tools through the separate version operation kinds and the version-specific source validator. List them using an explicit version subtype filter. Bind a reviewed pending-row update to its old digest and the same exact occurrence. If the native row key matches another occurrence, block companion submission rather than overwriting it. Reconstruct both version payloads with the canonical version helper, including DELTA and wrapped FULL, and authorize their nested sources before returning the diff. Test both snapshot forms, an archived or unavailable chain, owner approval, rejection and two occurrences of one definition. [Workspace collaboration](../../src/lib/character/workspace/collaboration.ts) · [Specific-slot version validation](../../src/lib/character/validate-version-proposal.ts) · [Version proposal submit](../../src/app/api/characters/%5Bid%5D/proposals/route.ts) · [Version proposal decision](../../src/app/api/characters/%5Bid%5D/proposals/%5BproposalId%5D/route.ts) · [Version reconstruction](../../src/lib/versions/version-payload.ts)

The staged adapter supports exact direct slots with complete accessible historical pins. It can apply supported scalar primitive changes and name or prose changes to capabilities and items with unchanged memberships. The native version bump keeps the existing materialized composition. Use the character sheet for inherited targets, incomplete history, composition changes, and mechanical capability or item changes. Enable `MCP_CHARACTER_VERSION_PROPOSAL_READS_ENABLED` and `MCP_CHARACTER_VERSION_PROPOSAL_WRITE_ENABLED` independently, with the Phase 2 flags and guarded fictional review environment. The website remains available for native version proposals during the staging rollout.

Use the shared write ordering and then recheck access, base fingerprint, pin set and expected result. For an owner-approved draft, resolve the exact active proposal author and require that author's current suggestion access. A soft-deleted author cannot execute. Nested draft calls join the same transaction. Throw on domain failures before leaving the owner transaction. Commit the revision or proposal outcome with the companion receipt. Invalidate dependent caches after commit. Use `get_operation_status` to reconcile a timeout. Present the stored outcome under current permissions and label any newer state separately. A stale approval requires a fresh review.

For a supported nested companion edit, store a grant for the verified private fork's exact direct root placement and version in the same transaction. The character viewer must retain their current role, access to the original source, and independent access to each member. Library and standalone definition visibility keep their existing behavior. Detaching or changing the pinned root ends that grant. Nested companion proposals apply through the same reviewed companion handler so the grant and receipt commit with the edit. Native rejection and withdrawal remain available.

### Reviewed level advancement

- `preview_character_advancement({ characterId, expectedRevision, targetLevel })` uses the canonical sheet to show the level thresholds, effective proficiency, maximum Vitality, volatility ceiling, and available and spent Build Units. The before and after pool include the character's custom starting BU floor and the native level-up's DM bonus reset. Its consequence for the available budget appears in the review.
- `prepare_character_advancement` creates a separate review with the same input and optional `supersedesOperationId`. It binds the exact owner, character, target level, starting revision, current build and derived result. The review covers up to 20 levels per operation. The owner can separately choose how to spend unlocked BU.
- `apply_character_advancement({ operationId })` rechecks that review under the character and publishing locks. It updates the level, consumes any existing DM bonus, bumps the workspace revision and records native history and a character version in the same transaction as the receipt. The four original Gale Reed acquisitions, backstory, and stored current Vitality stay intact. A second approval against the prior state needs a fresh review. A retry of the same operation returns the original result.
- Verify the restored fictional Gale Reed from L1 to L10. Expect 127 BU in the pool, 16 spent, 111 available, effective proficiency 4 and maximum Vitality 140. Test a custom starting budget above the next threshold and a changed grant after approval. Test non-owner roles, missing edit scope, preserved wounds and the full-Vitality marker, and exact replay.
